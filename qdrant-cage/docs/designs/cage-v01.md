## Vision

### 10x Check
CAGE becomes the `create-next-app` of agent-native development. One command (`cage init`)
and your project is structured so that any agent (Claude, Codex, Gemini) produces
production-quality output from day one. Not just scaffolding, but active enforcement:
contracts that can't drift, commands that can't be bypassed, features that follow a
lifecycle, audits that track staleness.

### Platonic Ideal
You clone any repo, run `cage init`, and CAGE analyzes the project structure, detects
services, infers contracts from existing code, generates execution policies from the
dependency graph, and produces agent context files that any agent could read and immediately
be productive. The user feels: "I didn't have to explain my codebase to the AI.
The cage already knows."

Checks are declarative rules, not shell scripts. The feature lifecycle is a state machine,
not disconnected skills. Every agent session is logged and auditable.

## Definition of Done

v0.1 ships when:
1. `cage init --template fullstack` produces a project where a fresh Claude Code or Codex session can run `/cage-spec`, `/cage-feature`, `/cage-review` without errors
2. `cage check` catches a real boundary violation, API snapshot mismatch, import bypass, or hardcoded value in a test fixture
3. `cage scan` correctly detects services in a monorepo with 3+ services and generates CLAUDE.md + AGENTS.md per service
4. `cage doctor` identifies at least 5 distinct setup issues (missing hooks, stale worktrees, incomplete contracts, etc.)
5. `cage merge` safely handles clean merges and refuses conflicting merges
6. Port slot offsets work across 3 concurrent worktrees with zero port collision
7. Feature pipeline blocks `/cage-feature` when spec is not approved
8. All unit tests pass, integration tests pass on a fixture project

## Implementation Approach

### Architecture: Shell dispatcher + single cage-core Bun binary

```
cage (shell script)
  |
  ├── Simple commands (merge, worktree) -> shell implementation
  └── Complex commands (all others) -> cage-core <subcommand> [args]

cage-core (compiled Bun binary, single file)
  ├── cage-core policy parse <rules-file>
  ├── cage-core policy check <command-string>
  ├── cage-core contract validate <shared-dir>
  ├── cage-core check run [--name <check>] <project-root>
  ├── cage-core check list
  ├── cage-core infra start <config-yaml>
  ├── cage-core infra stop <pid-dir>
  ├── cage-core port assign <service-name> <worktree-index>
  ├── cage-core pipeline get <feature-name>
  ├── cage-core pipeline transition <feature-name> <new-state>
  ├── cage-core scan <project-root>
  ├── cage-core doctor <project-root>
  └── cage-core init --template <T> <target-dir>
```

### Zero runtime dependencies
bash + git + the compiled cage-core binary. No python3, no Node.js, no external tools.
cage-core is compiled via `bun build --compile` into a standalone executable (~30-60MB).

### State locations
```
.cage/                    # per-project (gitignored)
  pipeline.json           # feature lifecycle state
  pids/                   # running service PIDs
  audits/                 # audit reports
  .prepared               # worktree bootstrap marker

~/.cage/                  # global
  config.yaml             # user preferences
```

### Feature Pipeline State Machine

```
  spec-created ──> spec-approved ──> worktree-prepared ──> implemented
                                                               |
                                                               v
                            merged <── reviewed <── tests-passing
```

Valid forward transitions:
- spec-created -> spec-approved (user approves spec)
- spec-approved -> worktree-prepared (/cage-feature runs cage worktree prepare)
- worktree-prepared -> implemented (/cage-feature completes implementation)
- implemented -> tests-passing (cage check passes AND project test command passes)
- tests-passing -> reviewed (/cage-review approves)
- reviewed -> merged (cage merge completes, triggers worktree cleanup)

Backward transitions (regression):
- tests-passing -> implemented (tests regress after code changes)
- reviewed -> implemented (review requests changes)
- Any state -> spec-created (via `cage pipeline reset <feature>`)

Invalid transitions are rejected with current state + valid next states.

`tests-passing` requires BOTH cage architectural checks AND the project's test
command (detected from package.json scripts.test or pyproject.toml [tool.pytest]).
cage-core discovers the test command and runs it.

### Skill Integration with Pipeline

Skills invoke `cage-core pipeline get <feature>` to check state before proceeding:
```bash
# inside /cage-feature skill
STATE=$(cage-core pipeline get user-profiles | jq -r .state)
if [ "$STATE" != "spec-approved" ]; then
  echo "error: feature 'user-profiles' is in state '$STATE'. run /cage-spec and approve first."
  exit 1
fi
```

Skills invoke `cage-core pipeline transition <feature> <state>` after completing work.

### cage merge Integration

`cage merge <branch>` wraps git merge --squash with:
1. Conflict check (refuses if conflicts detected)
2. Backup tag creation
3. Squash merge
4. `cage-core pipeline transition <feature> merged` (auto-detected from branch name feat/<name>)
5. `cage worktree clean` suggestion for the completed worktree

### cage.rules Syntax

```
# format: ACTION PATTERN [ALTERNATIVE]
# ACTION: block (reject), prompt (ask user), allow (explicit allow)
# PATTERN: tokenized command prefix (not substring match)
# ALTERNATIVE: suggested replacement command

block   next build              cage infra start
block   terraform apply         cage tf apply
prompt  git push
prompt  rm -rf
```

cage-core policy check tokenizes the input command and matches against rule
patterns token-by-token. "block kill" matches "kill 1234" but NOT "killall" or
"skill-builder". This eliminates the false positive problem from grep-based matching.

### Dual-Host Output

CLAUDE.md (for Claude Code) and AGENTS.md (for Codex) serve the same purpose:
giving the agent project context. They contain identical content but live at
different paths because each agent reads from a different location.

Generated by: `cage init`, `cage scan`
Updated by: user manually or `cage scan --update`

State persisted in `.cage/pipeline.json`:
```json
{
  "features": {
    "user-profiles": {
      "state": "implemented",
      "spec": "docs/features/user-profiles.md",
      "branch": "feat/user-profiles",
      "worktree": "../project-user-profiles",
      "created": "2026-03-21T10:00:00Z",
      "updated": "2026-03-21T14:00:00Z"
    }
  }
}
```

### Built-in Checks (exact list for v0.1)

| Check | What it does | Trigger |
|-------|-------------|---------|
| boundary-enforcement | Scans import statements. Flags any import from another service's internal modules. | Files in services/ directories |
| api-snapshot-validation | Compares API response shapes against shared/api-field-snapshots.json. | Changes to API handlers or shared/ |
| import-centralization | Ensures external API clients go through a central module, not direct imports. | Any new import of http/fetch/axios |
| hardcoded-value-detection | Flags literal values that match entries in shared/domain-values.json. | All source files |

Check module interface:
```typescript
interface CageCheck {
  name: string
  description: string
  category: 'contract' | 'architecture' | 'safety'
  run(projectRoot: string): Promise<CheckResult>
}

interface CheckResult {
  pass: boolean
  issues: Array<{
    severity: 'critical' | 'warning' | 'info'
    file: string
    line?: number
    message: string
    fix?: string
  }>
}
```

### cage scan (v0.1 scope: detection + scaffolding)

What cage scan does in v0.1:
1. Walk the project directory (respecting .gitignore)
2. Detect services by markers: package.json, pyproject.toml, Cargo.toml, go.mod, Dockerfile
3. For each detected service, identify framework by dependency inspection:
   - Next.js: package.json with `next` in dependencies
   - React (non-Next): package.json with `react` but no `next`
   - Express: package.json with `express` in dependencies
   - FastAPI: pyproject.toml with `fastapi` in dependencies
   - Flask: pyproject.toml with `flask` in dependencies
   - Django: pyproject.toml with `django` in dependencies or manage.py present
   - Go: go.mod present
   - Rust: Cargo.toml present
   - Unknown: marker file exists but no recognized framework dependency
   Also detect: entry point, test command, env vars (.env.example)
4. Generate per-service CLAUDE.md and AGENTS.md from a template, pre-filled with detected info
5. Print a summary: "detected 3 services: backend (FastAPI), frontend (Next.js), worker (Python)"

What cage scan does NOT do in v0.1 (deferred):
- Infer contracts from code
- Generate cage.rules from dependency graph
- Detect API shapes for api-field-snapshots.json

### Failure Modes

| Feature | Failure | Behavior |
|---------|---------|----------|
| cage init | Already initialized | Skip existing files, warn. Use --force to overwrite. |
| cage init | Template not found | List available templates, exit 1 |
| cage init | Not a git repo | Exit with "run git init first" |
| cage scan | No services detected | "No services detected. Is this the project root?" |
| cage scan | Unknown framework | Generate generic CLAUDE.md, note "framework: unknown" |
| cage check | Check module crashes | Catch error, report as check failure, continue other checks |
| cage check | shared/ missing | Skip contract checks, warn |
| cage infra | Port in use | Report which process holds the port, suggest alternate |
| cage infra | Service crashes on start | Show last 20 lines of .cage/<service>.log |
| cage merge | Conflicts | List conflicting files, refuse merge, suggest --dry-run |
| cage pipeline | Invalid transition | Show current state, list valid next states |
| cage doctor | Missing dependency | Report what's missing, suggest fix command |
| check-policy hook | Pattern false positive | Bun binary uses tokenized matching, not grep substring |

### Semantic Code Intelligence: Qdrant Edge + Jina Code

CAGE builds its own semantic code understanding layer instead of depending on
external tools like Serena. The stack:

- **Qdrant Edge**: in-process vector store (no daemon, no server, runs as library)
- **Jina Code v2**: code-specialized embeddings via FastEmbed (ONNX, local, no API keys)
- **cage-core**: orchestrates indexing, querying, and check execution

#### How it works

```
cage index (runs on project init, file change, or manually)
  |
  ├── Walk source files (respecting .gitignore)
  ├── Chunk code at multiple granularities:
  │   ├── File-level    (for cage scan: service detection, clustering)
  │   ├── Function-level (for checks: boundary enforcement, similarity)
  │   ├── Import-level   (for checks: import centralization, cross-service refs)
  │   └── Contract-level (shared/*.json -> vectors for drift detection)
  ├── Generate embeddings via Jina Code v2 (FastEmbed, ONNX, CPU-only)
  └── Store in Qdrant Edge (in-process, persisted to .cage/vectors/)
```

#### What this powers

```
cage-core check run
  ├── boundary-enforcement:
  │   Query: "find function-level embeddings from service A that are
  │           semantically similar to embeddings from service B's internals"
  │   Filter: by file path prefix (structured filter, not just vector similarity)
  │
  ├── hardcoded-value-detection:
  │   Query: "find code embeddings semantically similar to contract values"
  │   Hybrid: dense (semantic) + sparse (keyword match on literal strings)
  │
  ├── api-snapshot-validation:
  │   Query: "find API handler embeddings, compare response shapes to snapshots"
  │
  └── import-centralization:
      Query: "find all import-level embeddings referencing external HTTP clients"
      Filter: exclude the centralized client module

cage scan
  ├── Cluster file-level embeddings to auto-detect service boundaries
  ├── Find entry points (embeddings similar to "main", "app", "handler")
  ├── Detect API surfaces (embeddings similar to "route", "endpoint", "handler")
  └── Generate CLAUDE.md from semantic understanding of each cluster

cage search <query>    (NEW: semantic code search for agents)
  └── "find all authentication logic" -> ranked results with file:line
  └── "where is rate limiting implemented" -> semantic search across codebase
```

#### Hybrid Code Intelligence: Qdrant + Serena

CAGE uses hybrid code intelligence, the same concept as Qdrant's hybrid search
(dense + sparse), but applied to code understanding: vectors (semantic, broad,
probabilistic) + LSP (exact, narrow, deterministic).

```
cage-core check run
  |
  ├── Qdrant Edge (always available, ships with CAGE)
  │   └── semantic search, clustering, drift detection
  │
  ├── Serena MCP (optional, if user has it configured)
  │   └── exact symbol lookup, references, type hierarchy
  │
  └── Hybrid merge
      └── combine results, deduplicate, rank by confidence
      └── LSP confirms/contradicts vector results
      └── vectors catch what LSP misses (copied logic, semantic drift)
```

Serena integration: cage-core acts as an MCP client to Serena when configured.
User installs Serena separately (`cage doctor` detects and recommends it).
CAGE degrades gracefully without it: vector-only checks still work.

Configuration in cage project:
```yaml
# cage-config.yaml (optional)
serena:
  enabled: true
  # Serena MCP server connection
  command: "serena-mcp"
  args: ["--project", "."]
```

| Check | LSP contribution (Serena) | Vector contribution (Qdrant) |
|-------|--------------------------|------------------------------|
| boundary-enforcement | exact import resolution | detect copied/reimplemented logic |
| api-snapshot-validation | exact type shapes | detect semantic drift in patterns |
| import-centralization | exact import graph | find indirect HTTP calls (wrapped fetch) |
| hardcoded-value-detection | exact constant resolution | find semantically equivalent values |
| cage scan | exact module exports/entry points | cluster by semantic similarity |
| cage search | "go to definition" for results | natural language code search |

This hybrid approach fixes the main weakness of vector-only checks (probabilistic
accuracy) while gaining capabilities LSP alone can't provide (semantic similarity,
natural language queries, cross-language understanding, pattern clustering).

#### Storage

```
.cage/
  vectors/              # Qdrant Edge persistent storage
    collection.qdrant   # vector data
  index-meta.json       # last indexed commit, file hashes for incremental
```

Incremental indexing: on `cage index`, compare file hashes against index-meta.json.
Only re-embed changed files. Full re-index on `cage index --force`.

#### cage search (new command)

Agents can query the codebase semantically:
```bash
cage search "authentication middleware"
cage search "database connection pooling"
cage search "error handling for API timeouts"
```

Returns ranked results with file path, line range, relevance score, and code snippet.
This replaces grep for conceptual searches. Agents use it during /cage-feature to
understand existing patterns before implementing.

### Sequencing (implementation order)

```
Phase 0 (foundations):  Bun project setup, cage-core CLI scaffold, build system
Phase 1 (core):         policy parser, contract validator, cage init with templates
Phase 2 (vectors):      Qdrant Edge integration, Jina Code embeddings, cage index, cage search
Phase 3 (lifecycle):    pipeline state machine, cage merge (already works), worktree
Phase 4 (enforcement):  4 built-in checks (vector-powered), bypass detection, prepare-commit-msg
Phase 5 (intelligence): cage scan (vector-powered clustering), cage doctor, port slot system
Phase 6 (skills):       /cage-spec, /cage-feature, /cage-review, /cage-audit (update existing)
Phase 7 (polish):       dual-host setup, tests, documentation
```

Each phase blocks on the previous. CC time estimate: ~6-8 hours total.
Phase 1 is the heaviest (templates + binary scaffold). Consider shipping with
fullstack template only in v0.1.0, adding api + monorepo in v0.1.1.
Phase 2 is new: Qdrant Edge + FastEmbed integration is the core differentiator.
